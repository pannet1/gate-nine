Gate Nine — Single point of reference

Last updated: 2026-10-18

This page is the one place the team follows for how this project is designed and how it grows. It records the control flow and the conventions around it — not what to test or how to test. The brief is the source of what to test; the how lives in app/vouchers/<case>/test-case.html, and test.html holds only the order in which those cases run. Update this page in the same change that moves the design forward.

1. Aim & System Boundary

To see the browser entering data. Everything in this project is geared toward that one thing — watching Chromium open, watching fields get filled, and being able to step in and fix what looks wrong.

Rachis arrives already tested vigorously — around 1000 runs — before it lands here. Bug hunting is not this harness's job. Its job is visibility, so that Murugan and Jashveer can watch data being entered in real time (docs/DESIGN.md: "run the tests and see the browsers being opened up and fields entered").

Rachis stays an external black-box system — no source code, no internal APIs, no database access. A human writes the brief, a human approves it, and a human decides what they saw.

Consequence for design: never headless. A loop that hides the window defeats the only purpose of the project. Any change that makes data entry less observable is the wrong change.

Core Architectural Principles
  • Rachis is an External Black-Box: https://rachis.co.in is an external system with no source code access, no internal APIs, and no direct database connections. This repository owns only test definitions, browser execution, evidence, and diagnostic reporting.
  • Visible Browser at All Times: The browser runner is never headless (HEADLESS = False). Gate Nine's core purpose is visibility — allowing human stakeholders (Murugan, Jashveer, Karthick) to watch data entry live in Chromium.
  • Observation Pacing: A fixed delay (STEP_DELAY = 3s) between actions allows human eyes to follow inputs before subsequent operations execute.
  • Human Governance: An AI model never marks a run as passed. Human testers own the final PASS/FAIL decision, and the runner only creates or drafts vouchers authorized by a human-approved test brief.

3. Folder layout

Vouchers are canonical and live in app/vouchers/ — one folder per unique document, holding its test-case.html. A run never owns a voucher; it links to one.

app/vouchers/                 # canonical — one folder per unique document
├── login/
│   └── test-case.html
├── sales-invoice/
│   └── test-case.html
├── purchase-bill/
│   └── test-case.html
├── goods-receipt/
│   └── test-case.html
├── credit-note/
│   └── test-case.html
└── debit-note/
    └── test-case.html

Login is a case, not a voucher. It holds no voucher type and appears in no voucher phase — it is the door every other case walks through, so it lives here for the same reason the others do and is linked into every run. Every test.html opens with it.

A human creates a uniquely numbered run folder — the run_id, zero-padded (001, 002, …) — and drops in a Markdown brief plus symlinks to the vouchers under test. The runner never invents a run_id; it only ever reads the highest-numbered folder that already exists.

test-cases/
└── 001/                    # run_id — created by a human
    ├── <any-name>.md       # brief from Murugan — name is free, only .md matters
    ├── test.html           # the ordered plan — which case runs when, nothing else
    ├── events.jsonl        # archived run log (moved from root after run completes)
    ├── voucher.png         # current evidence screenshot
    ├── login           ->  ../../app/vouchers/login
    ├── sales-invoice   ->  ../../app/vouchers/sales-invoice
    ├── purchase-bill   ->  ../../app/vouchers/purchase-bill
    ├── goods-receipt   ->  ../../app/vouchers/goods-receipt
    ├── credit-note     ->  ../../app/vouchers/credit-note
    └── debit-note      ->  ../../app/vouchers/debit-note

Each symlink is ../../ — two levels up from the run folder reaches the project root.

The plan carries the order; the case folder carries the method. test.html says which case runs when — step, test number, action, and the folder that owns it. It states no steps, no checks, and no expected results, because those belong to app/vouchers/<case>/test-case.html and to nowhere else. Putting the how-to in the plan as well would mean the same method written twice, drifting apart the moment either copy is edited. If a step needs a different method, the case folder changes — not the plan.

Revised in place, not versioned. A voucher is one live document. A later run linking it sees whatever it says now, and revising it for a later run rewrites what an earlier run pointed at — accepted, because history is carried by the run's evidence, not by the document. Dead versions are not wanted.

The brief's filename is free — notes.MD, header-fields.md, whatever its author chose. Only the .md extension matters, because that is what the loop looks for.

4. Intended workflow

The application follows a strict 4-step human-supervised cycle: Step A → Step B → Step C → Step D.

Step Stage Owner Mechanism Primary Artifacts
Step A Human creates run Murugan / Tester Manual brief writing & run directory creation test-cases/<run_id>/<brief>.md
Step B Voucher training & plan prep Human + Playwright codegen + AI Live browser recording (30s) & AI plan packaging app/vouchers/<case>/test-case.html, test-cases/<run_id>/test.html
Step C Visible unattended execution Playwright Driver Visible Chromium (HEADLESS = False) + Playwright verbs events.jsonl → test-cases/<run_id>/events.jsonl
Step D AI diagnosis & triage AI Diagnostician app.diagnose automated inspection of log & plan Read-only triage report (harness vs product bug)
Step A — Human Creates the Run

A human writes the brief in Markdown and creates the next sequential run folder under test-cases/ (e.g. 001, 002). The system never invents a run folder or executes without a human-authored brief.

Step B — Fast Voucher Training via Playwright codegen & Plan Synthesis

Instead of having AI struggle to guess or generate brittle browser code from prose, Gate Nine utilizes Playwright's native codegen feature. This records real, resilient selectors (get_by_placeholder, get_by_role) directly from the live DOM in 30 seconds.

Why Playwright codegen Replaces Raw AI Code Generation
Dimension Traditional AI Code Generation Playwright codegen Workflow
Selector Accuracy AI guesses CSS/XPath selectors from text; prone to broken or hallucinated locators. Generates 100% accurate, resilient locators directly from live user actions.
Speed & Effort Iterative trial-and-error debugging over multiple context turns. Human tester or developer clicks through the form once in 30 seconds.
Role of AI Struggles to write raw browser automation from scratch without DOM access. Translates recorded code into standard verbs (open, input with name arrays, click, verify, screenshot).
Playwright codegen Commands & Storage State

1. Save authentication state once:

uv run playwright codegen --save-storage=auth.json https://rachis.co.in/login/

2. Record a new voucher flow pre-authenticated:

uv run playwright codegen --load-storage=auth.json https://rachis.co.in/accounting/sales-invoices/new/

3. Synthesize into Gate Nine plan: AI takes the recorded interactions, parameterizes fields into the ordered plan format in test.html, and updates the canonical voucher method in app/vouchers/<case>/test-case.html.

Step C — Main Loop Drives Visibly

The main runner (app.driver) executes the generated plan in a visible Chromium browser (HEADLESS = False):

  • Reads ordered steps from the machine-readable plan inside test.html.
  • Empties the temporary root events.jsonl before execution.
  • Drives forms using standard Playwright verbs: open, input (supporting regular fields and name arrays like ["item", "qty"] for line items), click, verify, and screenshot.
  • Between actions, holds for STEP_DELAY (3 seconds) for human observation.
  • On completion, crash, or interruption, archives the root log into test-cases/<run_id>/events.jsonl (cleanly overwriting any prior log).
events.jsonl                  # active root log during run
test-cases/001/events.jsonl   # archived after run completes
Step D — AI Diagnoses the Completed Run

When the run ends and both test.html and events.jsonl exist in the run folder, app.diagnose inspects the outcome:

  • Surfaces Playwright runtime diagnostics (console errors, uncaught exceptions, network failures, page crashes).
  • Verifies zero harness gaps (step_no_handler) in production runs.
  • Separates product defects from harness issues, keeping bug classification undetermined until human developer review.

5. Structured action & Playwright verb contract

All browser interactions are driven by standard Playwright verbs without ad-hoc custom verbs:

  • open: Navigates directly to routes (e.g. /accounting/sales-invoices/new/).
  • input: Fills header fields and line item table rows, supporting scalar fields and name arrays paired with value arrays for multi-column line item entry (e.g. ["item", "qty"] paired with ["Hamam", "2"]).
  • click: Interacts with buttons, tabs, and action controls (e.g. Save draft, Print, Post, ✕).
  • verify: Asserts page calculations, rendered elements, and tax summaries (e.g. verify tax).
  • screenshot: Captures evidence snapshots (voucher.png).

Sample Plan Step JSON Block (inside test.html):

{
  "phase": "C",
  "test": "Test 3",
  "action": "input",
  "name": ["item", "qty"],
  "value": ["Hamam", "2"],
  "case": "sales-invoice"
}

Strict Production Invariant: Zero Harness Gaps. Production runs must execute with 0 step_no_handler occurrences. Line items are represented as standard input verbs with column name arrays rather than legacy custom verbs like add_line.

Operation Logging Format: Every operation logs to JSONL following the pattern: operation <name:value> <form name> (e.g. input item:Hamam sales-invoice, click Save draft sales-invoice).

6. Main loop details

Playwright drives; the human watches. The run is unattended — nothing prompts, and nothing waits for a keystroke.

  1. Find the latest run_id — the highest-numbered folder under test-cases/.
  2. Discover the .md file from Murugan inside it. The name is irrelevant; only its presence counts.
  3. Proceed with test.html. If it is absent, the tester or AI records the live interaction via Playwright codegen, and the AI synthesizes the ordered plan (test.html) and canonical method (app/vouchers/<case>/test-case.html) — the system never guesses or hallucinates selectors.
  4. Open Chromium visible, never headless (§1).
  5. Read the machine-readable plan block inside test.html and execute its steps in order using standard Playwright verbs (open, input, click, verify, screenshot). Line items are treated just like regular fields using name arrays (e.g. ['item', 'qty']). Legacy add_line pseudo-actions are eliminated, ensuring production runs execute with zero harness gaps.
  6. Between steps the runner holds for a fixed delay — step_delay, default 3 seconds, set by STEP_DELAY — so human eyes can follow what was just entered before the next action fires.
  7. An unsupported action is recorded and stops the run as incomplete. Merely opening a form is not counted as completing its test.
  8. A step that genuinely fails stops the run there, per the Run Lifecycle (§7). The browser closes and the terminal returns.
  9. Every step's outcome is written to the append-only JSONL event log. A summary is printed when the run ends.
  10. uv run python -m app.watch tails the root events.jsonl to a second terminal, so the run can be followed without looking at the browser.
  11. uv run python -m app.diagnose inspects the completed run folder for Step D, verifying that test.html and events.jsonl are present, surfacing unhandled actions, failed steps, and Playwright error diagnostics before human-in-the-loop review.

No .md file in the run folder means the loop does not proceed. It does not guess and does not fall back to any other source.

7. Lifecycle

Case Lifecycle

draft → codegen-recorded → ai-prepared → human-approved → running → passed | failed

  • draft: Voucher document or brief proposed.
  • codegen-recorded: Live tester actions recorded via playwright codegen with 100% accurate DOM selectors.
  • ai-prepared: Parameterized actions formatted into canonical test-case.html and plan.
  • human-approved: Human confirms test data and authorized voucher mutations.
  • running: Executed visibly by Playwright.
  • passed | failed: Final verdict decided by verification checks and human review.
Run Lifecycle

brief-present → plan → running → incomplete | failed | passed

  • incomplete: The runner stops immediately on any unsupported action. Merely opening a voucher never counts as a test pass.
  • failed: A step failure stops the run immediately to avoid compounding errors.
  • passed: A run is only marked passed when all steps succeed and at least one verification check (verify) has executed.

A failed or incomplete run is not resumed. The next attempt is a fresh run_id (002, 003, …) with the corrected brief or harness.

8. Logging & two-phase log lifecycle

Logging follows a strict two-phase lifecycle separating active execution from permanent archive:

  1. Active Run Log (events.jsonl at root): Emptied before execution begins. Every operation is appended here in real time. Developers and testers tail live progress in a secondary terminal via uv run python -m app.watch.
  2. Archived Run Log (test-cases/<run_id>/events.jsonl): Upon run completion, crash, or interrupt cleanup, the root file is moved into the run folder, cleanly overwriting any prior log from previous attempts.

Every operation is logged as operation <name:value> <form name>:

input product:hamam voucher
create screenshot voucher
save screenshot voucher
delete screenshot voucher
click home delivery note

Logs are append-only JSONL and carry action, dynamic step number, safe details, and timestamp. The run folder is the run identity; no separate test ID is recorded. Each step logs one step_setup, step_ok, step_no_handler, or step_failed event; a run ends with a run_result event carrying counts and final status (passed, incomplete, or failed). During the run, Playwright diagnostics (playwright_console_error, playwright_page_error, playwright_request_failed, playwright_page_crash) are recorded with active step context. The team wants a live relay of the current operation so Murugan and Jashveer see real-time progress.

9. Infra

  • Remote terminal-only compute for the developers to watch the live log.
  • A web server alongside the log, presenting the run's files in a rich HTML interface — screenshot, brief, and test plan together.
  • Local harness: FastAPI service (app/) with /health, /api/events, and a dashboard at http://127.0.0.1:8000.
  • app.driver is the sole browser runner and remains separate from the FastAPI dashboard so voucher-specific behaviour does not mix into the API.
  • app.diagnose is the read-only post-run diagnosis gate (Step D) that inspects the latest run folder and surfaces harness gaps or browser errors, keeping product-bug classification undetermined until human browser review.
  • Runtime data is gitignored: .env, data/, and every run-local screenshot. Evidence may quote tenant data, so it is never committed.

10. Safety

  • Never commit .env, tenant credentials, customer data, or unredacted evidence.
  • The runner may open and inspect the tenant but must not create or post a voucher unless a human approved that specific case and its test data.
  • A human owns the final PASS/FAIL — an AI model never marks a run as passed.
  • The AI writes test.html; the main loop writes the run log and evidence files. The human writes the brief and controls the approval/training decisions.
