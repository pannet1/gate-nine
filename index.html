Gate Nine — Single point of reference

Last updated: 2026-10-17

This page is the one place the team follows for how this project is designed and how it grows. It records the control flow and the conventions around it — not what to test or how to test. Those live in the brief and in the generated test.html. Update this page in the same change that moves the design forward.

1. Aim

Final functional testing of https://rachis.co.in before delivery to the customer. Rachis is treated as an external black-box system — no source code, no internal APIs, no database access. Testing is human-in-the-loop: a human writes the brief, a human approves it, and a human owns the final PASS/FAIL.

3. Folder layout

Vouchers are canonical and live in app/vouchers/ — one folder per unique document, holding its test-case.html. A run never owns a voucher; it links to one.

app/vouchers/                 # canonical — one folder per unique document
├── sales-invoice/
│   └── test-case.html
├── purchase-bill/
│   └── test-case.html
├── goods-receipt/
│   └── test-case.html
└── credit-note/
    └── test-case.html

A human creates a uniquely numbered run folder — the run_id, zero-padded (001, 002, …) — and drops in a Markdown brief plus symlinks to the vouchers under test. The runner never invents a run_id; it only ever reads the highest-numbered folder that already exists.

test-cases/
└── 001/                    # run_id — created by a human
    ├── <any-name>.md       # brief from Murugesan — name is free, only .md matters
    ├── test.html           # the ordered test plan
    ├── sales-invoice ->  ../../../app/vouchers/sales-invoice
    ├── purchase-bill ->  ../../../app/vouchers/purchase-bill
    ├── goods-receipt ->  ../../../app/vouchers/goods-receipt
    └── credit-note   ->  ../../../app/vouchers/credit-note

Revised in place, not versioned. A voucher is one live document. A later run linking it sees whatever it says now, and revising it for a later run rewrites what an earlier run pointed at — accepted, because history is carried by the run's evidence, not by the document. Dead versions are not wanted.

The brief's filename is free — notes.MD, header-fields.md, whatever its author chose. Only the .md extension matters, because that is what the loop looks for. The artefacts below test-case.html are written as the run executes.

4. Main loop

The whole of it:

  1. Find the latest run_id — the highest-numbered folder under test-cases/.
  2. Discover the .md file from Murugesan inside it. The name is irrelevant; only its presence counts.
  3. Proceed with test.html.
  4. If test.html is not present, create it.
  5. Run the cases it defines, in its order.
  6. Stop dead on the first failure. No further case is attempted; the run ends there and the developers are notified.
  7. Finish only when every case in the run has passed.

No .md file in the run folder means the loop does not proceed. It does not guess and does not fall back to any other source.

5. Lifecycle

Per case: draft → ai-prepared → human-approved → running → passed | failed

Per run: brief-present → plan → running → failed on the first failing case, or passed when every case in the folder has passed.

A failed run is not resumed. The next attempt is a fresh run_id (002, 003, …) with the corrected brief.

6. Logging

Every operation is logged as operation <name:value> <form name>:

input product:hamam voucher
create screenshot voucher
save screenshot voucher
delete screenshot voucher
click home delivery note

Logs are append-only JSONL and carry test ID, action, safe details, and timestamp. The team wants a live relay of the current operation so Murugan and Jashveer see real-time progress.

7. Infra

  • Remote terminal-only compute for the developers to watch the live log.
  • A web server alongside the log, presenting the run's files in a rich HTML interface — screenshot, brief, and test plan together.
  • Local harness: FastAPI service (app/) with /health, /api/events, and a dashboard at http://127.0.0.1:8000.
  • Browser runner is kept separate so voucher-specific behaviour can be added without mixing into the dashboard.

8. Safety

  • Never commit .env, tenant credentials, customer data, or unredacted evidence.
  • The runner may open and inspect the tenant but must not create or post a voucher unless a human approved that specific case and its test data.
  • A human owns the final PASS/FAIL — an AI model never marks a run as passed.
  • The loop writes test.html, result.md, and the evidence files. The human writes the brief and the approval.
