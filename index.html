Gate Nine — Single point of reference

Last updated: 2026-10-18

This page is the one place the team follows for how this project is designed and how it grows. It records the control flow and the conventions around it — not what to test or how to test. The brief is the source of what to test; the how lives in the recorded <case>.py inside the run folder. Update this page in the same change that moves the design forward.

1. Aim & System Boundary

To see the browser entering data. Everything in this project is geared toward that one thing — watching Chromium open, watching fields get filled, and being able to step in and fix what looks wrong.

Rachis arrives already tested vigorously — around 1000 runs — before it lands here. Bug hunting is not this harness's job. Its job is visibility, so that Murugan and Jashveer can watch data being entered in real time (docs/DESIGN.md: "run the tests and see the browsers being opened up and fields entered").

Rachis stays an external black-box system — no source code, no internal APIs, no database access. A human writes the brief, a human approves it, and a human decides what they saw.

Consequence for design: never headless. A loop that hides the window defeats the only purpose of the project. Any change that makes data entry less observable is the wrong change.

Core Architectural Principles
  • Rachis is an External Black-Box: https://rachis.co.in is an external system with no source code access, no internal APIs, and no direct database connections. This repository owns only test definitions, browser execution, evidence, and diagnostic reporting.
  • Visible Browser at All Times: The browser runner is never headless (HEADLESS = False). Gate Nine's core purpose is visibility — allowing human stakeholders (Murugan, Jashveer, Karthick) to watch data entry live in Chromium.
  • Observation Pacing: A fixed delay (STEP_DELAY = 3s) between actions allows human eyes to follow inputs before subsequent operations execute.
  • Human Governance: An AI model never marks a run as passed. Human testers own the final PASS/FAIL decision, and the runner only creates or drafts vouchers authorized by a human-approved test brief.

3. Folder layout

The brief is the only input document. Murugesan writes a Markdown brief describing the testing workflow — which vouchers, in what order, and what each one must prove. A human creates the next sequential run folder and drops the brief in. The brief's filename is free — notes.MD, header-fields.md, whatever the author chose. Only the .md extension matters, because that is what the loop looks for.

The runner never invents a run_id; it only ever reads the highest-numbered folder that already exists, and never executes without a human-authored brief.

There is no plan file. test.html is gone. It existed only to tell an AI which verbs to synthesise, and with recorded code there is nothing left to synthesise. The recording is the test.

test-cases/
└── 001/                    # run_id — created by a human
    ├── <any-name>.md       # brief from Murugesan — the only input document
    ├── sales-invoice.py    # recorded flow, produced by codegen
    ├── purchase-bill.py    # recorded flow, produced by codegen
    ├── auth.json           # saved auth state, reused by every replay
    └── voucher.png         # current evidence screenshot

Recordings live inside the run folder. They are not canonical and not shared between runs. Run 002 carries its own copies; when the product changes, a run re-records against the current DOM rather than inheriting selectors that may no longer resolve. History is carried by the run's evidence, not by a shared document.

The brief says what to test. The recording is how. The brief carries the workflow; each <case>.py carries the exact interactions for that case. Neither restates the other.

4. Intended workflow

The developer provides a testing workflow. The loop records a new test, or replays a recorded one, and repeats until every test passes.

Step A — Human Provides the Workflow

Murugesan writes the brief in Markdown — which vouchers, in what order, and what each must prove — and a human creates the next sequential run folder under test-cases/ (e.g. 001, 002). This brief is the first and only input document the loop receives.

The system never invents a run folder, and never executes without a human-authored brief. No .md file means the loop does not proceed — it does not guess and does not fall back to any other source.

Step B — Record a New Test via Playwright codegen

A test that does not yet exist is driven manually by a human, with codegen recording. The recording captures real, resilient selectors (get_by_placeholder, get_by_role) directly from the live DOM, so nothing is guessed or hallucinated.

The run halts the moment a bug is found. During this step the human is the detector — they are watching the screen, and they stop. That is the whole bug-detection mechanism at record time.

Why codegen Replaces AI-Written Selectors
Dimension AI-written selectors codegen recording
Selector Accuracy AI guesses CSS/XPath from prose; prone to broken or hallucinated locators. Records locators directly from live user actions.
Speed & Effort Iterative trial-and-error across multiple turns. The human clicks through the form once.
Role of AI Writes raw browser automation without DOM access. None during recording. The human drives; the machine records.
Commands & saved authentication state

1. Save authentication state once, into the run folder:

uv run playwright codegen --save-storage=auth.json https://rachis.co.in/login/

2. Record a voucher flow, already authenticated:

uv run playwright codegen --load-storage=auth.json -o sales-invoice.py https://rachis.co.in/accounting/sales-invoices/new/

Login is infrastructure, not a test. It is saved once and loaded on every recording and every replay, so no recording carries a login flow of its own.

Step C — Replay a Recorded Test

A test that already exists is played back by executing its recording in a visible Chromium browser (HEADLESS = False, §1):

  • Load auth.json so the run starts already signed in.
  • Execute <case>.py as written — the same calls, in the same order, against the same selectors.
  • POST every operation as an event to events_url over HTTP Basic Auth (nothing is written to a local log).
  • Hold STEP_DELAY (3 seconds) between operations so a human can follow what was entered.

Configure the remote endpoint in .env: EVENTS_URL and EVENTS_PASSWORD. When EVENTS_URL is empty, events are not recorded.

Step D — Inform the Developer, and the Loop Repeats

A bug surfaces in one of two ways, and the two are different because the two kinds of run are different:

  • During recording (Step B) — the human decides. They are watching and they halt. No automation is involved.
  • During replay (Step C) — the recording threw. That is the bug.

Either way the developer is informed: the event stream carries it, and the terminal prints a summary naming the case and what failed.

Replay detects a broken flow. It does not judge whether a number is right — that judgement is the human's, made by watching.

The developer fixes the product and re-runs. The loop breaks when every test passes.

5. Recording contract

Each case is its own folder, holding the real URL, the recording, and the evidence:

test-cases/<run>/<case>/
├── url.txt          # the real URL — never guessed
├── <case>.py        # the recording
└── screenshot.png   # evidence — this name never changes

A recording is ordinary Playwright code. It is executed, not interpreted — the runner imports nothing from it. What a recording contains is what a recorded test does.

  • Navigation: page.goto() to the URL in url.txt.
  • Input: get_by_placeholder(), get_by_label(), get_by_role() — whatever the DOM actually offered at record time.
  • Interaction: click(), press(), select_option() on buttons, tabs, and action controls.

Invariants.

  • No selector is ever written by the AI. Every locator in a recording came from a human clicking the real DOM.
  • The URL is never guessed. It is read from url.txt. A missing url.txt means the URL is unknown and the step cannot proceed.
  • The screenshot line is appended by the AI, immediately before the form submit, as page.screenshot(path="screenshot.png") — a bare filename so it resolves into the case's own folder. The human never takes it by hand.
  • Login is never in a recording. It is loaded from auth.json.

6. Main loop details

Playwright replays; the human watches. A replay is unattended — nothing prompts, and nothing waits for a keystroke.

  1. Find the latest run_id — the highest-numbered folder under test-cases/.
  2. Discover the .md file from Murugesan inside it. The name is irrelevant; only its presence counts. Without it, the loop does not proceed.
  3. Find every <case>/ subfolder in the run folder. Each one is a test that already exists.
  4. Open Chromium visible, never headless (§1).
  5. Load auth.json so every recording starts signed in.
  6. Run each <case>.py in turn, exactly as written, one at a time — the tenant is shared state, so never in parallel. No interpretation, no substitution of values, no synthesis.
  7. Hold STEP_DELAY (3 seconds) between operations so human eyes can follow what was just entered before the next action fires.
  8. POST every operation as an event to events_url over HTTP Basic Auth. Nothing is written to a local log.
  9. screenshot.png is written into that case's own folder, so two cases never overwrite each other's evidence.
  10. An uncaught throw stops that recording, is reported by case and message, and ends the run.
  11. When every recording completes, the browser closes, the terminal returns, and the loop breaks.

7. Lifecycle

Test Lifecycle

briefed → recorded → running → passed | failed

  • briefed: The workflow names the test. No code exists yet.
  • recorded: A human drives it manually with codegen recording on, writing <case>.py into the case folder. The AI then appends the screenshot line before the form submit. The test now exists and can be replayed.
  • running: Executed visibly by Playwright from the recording.
  • passed: The recording ran to completion and the human saw nothing wrong.
  • failed: The recording threw, or the human saw wrong behaviour. The developer is informed and fixes the product.
Run Lifecycle

brief-present → recording → replay → failed | passed

  • brief-present: A human-authored .md exists in the run folder. Without it the loop does not proceed.
  • recording: Tests not yet recorded are driven manually, with codegen on, halting when a bug is found.
  • replay: Recorded tests are played back unattended in visible Chromium, one at a time.
  • failed: A recording stopped on a throw. The developer is informed.
  • passed: Every recording in the run completed and the human saw nothing wrong. The loop breaks.

A failed run is not resumed. The developer fixes the product and re-runs; the next attempt is a fresh run_id (002, 003, …) with its own recordings made against the current DOM.

8. Logging & remote event streaming

Every operation is POSTed as an event to the remote FastAPI endpoint configured in events_url over HTTP Basic Auth. No local event log is kept.

Every operation is logged as operation <name:value> <form name>:

input product:hamam voucher
create screenshot voucher
save screenshot voucher
delete screenshot voucher
click home delivery note

Logs carry action, dynamic step number, safe details, and timestamp. Each step logs one step_setup, step_ok, step_no_handler, or step_failed event; a run ends with a run_result event carrying counts and final status (passed, incomplete, or failed). During the run, Playwright diagnostics (playwright_console_error, playwright_page_error, playwright_request_failed, playwright_page_crash) are recorded with active step context. Request query strings and fragments are omitted. The team wants a live relay of the current operation so Murugan and Jashveer see real-time progress.

9. Infra

  • Pure CLI: Browser execution, event logging, and diagnostics operate via local Python CLI commands. Events are streamed to events_url over HTTP Basic Auth; nothing is written to a local log.
  • Remote terminal-only compute for the developers to watch the live event stream via the remote endpoint (or any httpd-protected log viewer).
  • app.driver is the sole browser runner, replaying recordings in visible Chromium and POSTing events remotely.
  • Runtime data is gitignored: .env and every run-local screenshot. Evidence may quote tenant data, so it is never committed.

10. Safety

  • Never commit .env, tenant credentials, customer data, or unredacted evidence.
  • The runner may open and inspect the tenant but must not create or post a voucher unless a human approved that specific case and its test data.
  • A human owns the final PASS/FAIL — an AI model never marks a run as passed.
  • No AI writes selectors. Recordings are produced by a human driving the live DOM; the runner only executes them. The human writes the brief and decides PASS/FAIL.
