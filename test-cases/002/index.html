Before you start

Which tenant. Use Fortune Electronics, or another tenant already confirmed to have the Work module enabled. Do not use the Zigma Infosoft demo tenant — Task/Helpdesk is scheduled last in that rollout and may have no Work entitlement or seed data.

  • Two accounts. One broad role (owner, or any role holding work:sla_policy:read) to reach admin and reporting surfaces; one narrow operational role (technician/agent) to confirm admin screens are correctly hidden.
  • Cookies are automatic. Rachis uses HttpOnly cookies (at, rt, csrf). Logging in through the browser sets all three — you only handle cookies yourself if you hit the API directly with curl.

If something is missing, check this first

Almost never a missing feature. In order of likelihood:

  1. Your role lacks the permission key. See the permission table below.
  2. The tenant is not on the latest schema.
  3. Stale manifest cache (~60s). Wait a minute and retry.

3. SLA engine

▣ Core engine verified 2026-08-14, sitting on business-hours calendars and contract→SLA binding.

  • Policy versions. Policies are versioned; publishing a new version archives the old one. Only a draft is editable — published and archived versions are read-only. Create a new version and confirm the old one locks.
  • Escalation ladder. Steps with time-based targets (assignee → owner → role → named user). Editable only on a draft. Fire one by letting a short test policy's target lapse.
  • ◐ Pause on wait states. An item entering a state flagged as "pausing" (e.g. Waiting on customer) should stop the SLA clock, and resume correctly on leaving. Code shipped, no confirmed founder walk — test deliberately.
  • Breach behaviour. Once a clock breaches it stays marked breached even if later events make a resolution look on-time. It never resets. Confirm it does not silently clear itself.

4. Approvals

▣ Verified 2026-10-04 on Fortune Electronics. Confirmed working:

  • A banner reading "Step N of M" while an approval is in progress.
  • Approve / Reject actions, each requiring the real approver — no impersonation.
  • Submit-for-approval action.
  • The item's state is gated — it cannot move to Done while an approval is pending.
  • An approval History showing real names, not IDs.
  • The list of eligible approvers is access-controlled — only people allowed to approve see or act on that step.
  • A blocked item is checked and refused at the final approval step, not silently allowed through.

Prerequisite: to test the notification side you need a work item type that has an approval chain configured — not every work type does. If no approval option appears on an item, ask whoever set up the tenant's work types before concluding it is broken.

5. Reports & Dashboard

▣ Verified 2026-09-29 on Fortune Electronics. Reached via Work → Dashboard — this is the module's own dashboard, not the general company dashboard. It is also what the older Service Reports nav item now redirects to.

ReportWhat it measures
SLA ComplianceFirst-response and resolution SLA outcomes per period
Mean Time to Resolution (MTTR)Time from creation to first resolution per period
First-Time Resolution (FTR)Share of resolved work not reopened since
CSAT SummarySatisfaction requests sent, response rate, average rating per period
Technician PerformanceOpen load, resolved count, resolution time per technician
  • Dashboard shows tiles (Open / SLA / Due / KPIs) plus an At-risk panel — items approaching an SLA breach light up there in real time. This is currently the only place SLA risk is visible in the UI.
  • There is no Overdue and no Awaiting-approval tile. Do not expect them.
  • If a report or the dashboard looks empty: check work:work_item:read (Dashboard) or the matching reports:work_*:read key (each report has its own) before assuming it is broken.
